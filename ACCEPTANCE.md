### No-fork boundary and the user's maintenance direction

The user selected a fixed pause window, with start/duration supplied **before running**. The continuous supervisor now renews short leases under unchanged identity, including a long pause; ordinary bounded commands retain their ten-minute limits. This can work as a cooperative operating procedure: the write worker drains and clears owned providers before reporting `paused_empty`; refresh is allowed operationally only after that confirmation. At window end, `resume: unchanged` checks the same config/rules/core/lease/path and resumes only that unchanged generation. `resume: manual` remains paused. Actual config/core changes require new ownership and an explicit restart; no automatic adoption is implemented.

Pinned official FlClash `68c71b8ef9b7486a224972eb371ff153c6b2de0f` has startup auto-update ([bootstrap](https://github.com/chen08209/FlClash/blob/68c71b8ef9b7486a224972eb371ff153c6b2de0f/lib/bootstrap.dart#L152)), a twenty-minute timer ([application](https://github.com/chen08209/FlClash/blob/68c71b8ef9b7486a224972eb371ff153c6b2de0f/lib/application.dart#L137)), GUI/profile/script/settings changes and explicit core restart. The profile updater checks elapsed intervals and directly schedules apply ([profiles](https://github.com/chen08209/FlClash/blob/68c71b8ef9b7486a224972eb371ff153c6b2de0f/lib/providers/actions/profiles.dart#L43)). This is not an exact wall-clock acknowledgement mechanism. The [setup path](https://github.com/chen08209/FlClash/blob/68c71b8ef9b7486a224972eb371ff153c6b2de0f/lib/providers/actions/setup.dart#L596) writes YAML before core setup; `preloadInvoke` does not expose an earlier external barrier. The [QuickJS host](https://github.com/chen08209/FlClash/blob/68c71b8ef9b7486a224972eb371ff153c6b2de0f/plugins/rust_api/rust/src/script/mod.rs#L18) supplies console bindings and pure JSON transformation, not a drain HTTP client.

Thus no source-backed claim can be made that unmodified FlClash automatically aligns all refreshes with the window. Manual/startup/out-of-window refresh, crashes, clocks and delays remain hazards; a fixed delay is not a verified drain acknowledgement. Turning off per-profile auto-update would not remove all other paths, and has **not** been performed or authorized. Existing check-before-write protection detects many changes but leaves a non-atomic check/PUT interval.

No private FlClash/Mihomo fork is required for the implemented pause mode or proposed exclusive-core design, and none is introduced. The remaining behavior choices are explicit: accept cooperative windows and manual fresh ownership after actual refresh; or change the workflow so an implemented agent launcher exclusively owns official unmodified Mihomo, with FlClash not simultaneously controlling it. Keeping unrestricted FlClash control with a guaranteed barrier needs an official upstream coordination facility (or a separately proven redesigned generation protocol). No such alternative is already implemented or proved by this audit. A private fork is not an implicit option.

## Completed separately authorized execution: disposable Windows core TUN

The new `scripts/tun_acceptance.py` defaults to an inert JSON plan. Running it without flags never queries host networking, binds sockets or starts a process. Actual execution requires `--execute --allow-isolated-tun`, an administrator session and the expected GitHub-hosted Windows runner/repository identifiers. The environment checks prevent accidental host/self-hosted execution; they are not a cryptographic attestation. Do not forge them to run on a personal computer.

The prepared `.github/workflows/owned-windows-tun.yml` runs only when the exact label `accept-core-tun-on-hosted-windows` is added to this repository's PR #5 from `codex/review-dns-correctness`. Publishing this workflow, a normal push or ordinary PR CI does not grant permission or launch the test. Add that label only after explicit approval of the following operation:

- One disposable `windows-2025` standard hosted VM; 20-minute job timeout. Estimated execution 5–15 minutes, not a measured result.
- Download Go/dependencies and the official Mihomo v1.19.32 Windows ZIP into the guest, checking the pinned archive SHA256. No host installation or Windows VM image is needed.
- Create an owned guest Wintun adapter and route only `198.19.0.0/16` to it. System proxy is untouched; no firewall change, default-route replacement, real subscription, API key or paid model is used.
- Resolve synthetic `.test` fixtures against a guest loopback DNS service, then connect ordinary native sockets to the Fake-IP address. Require the Windows route to point to the owned adapter and actual core metadata to report `Tun`, with expected MATCH/AND chains and original-rule priority.
- Repeat the observer's crash/restart/TTL/graceful-cleanup tests; compare guest default routes, existing-adapter DNS and owned-prefix routes before/after. Unexpected changes or failed cleanup fail the job. Terminate only recorded child PIDs; the platform discards the guest afterward.
- Emit only synthetic JSON results to workflow logs. No artifacts/caches/custom images or GitHub Release are created by this acceptance job.

No paid cloud account is requested.
